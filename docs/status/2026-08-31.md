# П'ятниця, 31.08.2026 — Roles, Permissions, Restrictions & End-to-End AI Review

Останній день Week 3. Мета — не додавати нові екрани, а звести результати понеділка-четверга в
цілісну систему і перевірити, що нові AI- та permission-концепції нічого не ламають у вже
збудованому Guardian.

## 1. Roles & Permissions matrix

Побудували таблицю **Сторінка × Тип дозволу** для всіх 10 розділів Guardian (Dashboard, All Nodes,
Node Detail, Detected Drift, Policies, Reports, Scan Schedules, CM Groups, Credentials,
Integrations) плюс окремий рядок AI interactions, по 8 типах дозволу: View · View data · Create ·
Edit · Delete · Execute · Use AI · Apply AI action.

Свідомо **не** проєктували повну рольову систему з іменованими ролями (Admin/Analyst/Viewer тощо) —
за прямим рішенням: спершу зрозуміти, які дозволи взагалі існують по кожній сторінці, а вже потім
(окремим кроком, не цього тижня) мапити їх на конкретні ролі.

Ключове правило, яке зафіксували: **Use AI і Execute — різні дозволи, не змішувати.** Користувач
може мати доступ до "Explain with AI" на проваленому check, не маючи права сам виконати дію
(Reconcile / Apply fix) — пояснення й виконання розв'язуються окремо.

Матриця будувалась на реальних функціях з коду (`credSave`, `credDelete`, `cmCreateGroup`,
`scanNodeRow`, `resumeNodeScans`, `pcFinishCreate`), а не абстрактних описах. Під час цього
знайшли gap: **у CM Groups немає функції видалення групи взагалі** (`cmDeleteGroup` не існує в
коді) — отже нема що обмежувати правом, поки цієї функціональності немає.

## 2. UX для обмежених дій — 4 стани

Зафіксували чотири канонічні стани для дій без дозволу:

- **Hidden** — фіча ховається повністю, коли користувач не мав би навіть знати про її існування.
  Застосовується до сторінкового View без права, і **завжди** до AI-тригерів без права (сама
  наявність AI-інсайту — цінність, яку не варто "дражнити" сірою кнопкою).
- **Disabled + explanation** — кнопка є, сіра, з поясненням чому недоступна. Для дій, де важливо,
  щоб користувач знав про існування дії (Execute на Detected Drift, Disconnect на Integrations).
- **Read-only** — весь об'єкт доступний на перегляд, редагування — ні, як цілісний стан сторінки
  (Node Detail, Policies), а не купа окремо задизейблених полів.
- **Permission required** — дія концептуально доступна, але вимагає підвищеного доступу через
  окремий запит, а не просто "сіра кнопка". Резервується для дій з високим ризиком: Credentials
  Create **і** Delete (створення/видалення секретів), Scan Schedules Delete (зупиняє заплановані
  скани).

Пройшлись по 4 реальних сценаріях (Policy Detail, Detected Drift, Node Detail, Credentials),
призначивши кожній конкретній дії один із цих чотирьох станів з обґрунтуванням.

**Все це — аналіз/таблиці в чаті, без жодних правок у `index.html`.** Свідоме рішення: не
реалізовувати повну permission-систему в коді цього тижня, лише зафіксувати модель.

## 3. End-to-End AI Review (Einstein / Bertha / Jupiter)

Перевірили в коді всі 5 AI-точок (Dashboard, Node Detail, Detected Drift = Einstein, Policy Detail
= Jupiter, Failed Scan = Bertha) на структурну консистентність:

- **Close/Back/Cancel:** усюди однаково — явний ✕ (`.ai-panel-close`) і клік поза панеллю
  (`_aiBindOutsideClose`) обидва ведуть до того самого `*AiDismiss()`. Жодна AI-панель не є
  модалкою й нікуди не навігує — закриття просто згортає її, користувач лишається на тій самій
  сторінці. Відповідає правилу AI Interaction Standard: AI ніколи не забирає екран.
- **Escape-клавіша:** не працює в жодній із 5 точок. Перевірили окремо — канонічна модалка
  (`openModal()`) Escape ловить, але жоден інший non-modal дропдаун у застосунку (`scan-menu-trigger`,
  `pd-filter-menu`) теж не ловить. AI-панелі структурно дропдаун, не модалка — відсутність Escape
  тут не розсинхрон, а збіг із наявною конвенцією.
- **Retry:** 4 з 5 точок (Dashboard/Drift/Failed Scan/Policy) ідуть через спільний `_aiRunPanel`
  (Week 3, Чт). Node Detail має свою реалізацію навмисно — вона демонструє всі 4 виходи (success/no
  result/error/unavailable) через demo-selector для перегляду. Візуально й текстово Retry
  ідентичний в обох варіантах (`.ai-inline-cta`, той самий стиль помилки).

Нових багів не знайдено — четверговий рефакторинг (`_aiRunPanel`) уже закрив реальні
неконсистентності. Цей прохід підтверджує стан, не змінює його.

## Не зроблено / відкрито

**Enterprise-only functionality (пункт 2 первинного плану п'ятниці) — не закрито.** У коді немає
жодної концепції продуктового tier (перевірено `grep -i enterprise|tier|upgrade` — лише збіги "OS
Enterprise" і "Database tier" як назви, не мають стосунку до ліцензування). Без конкретного
прикладу Enterprise-only функції в Guardian (від клієнта чи команди) цей пункт не реалізовували —
вигадувати state з нуля без референсу суперечило б підходу "не вигадувати, переюзати наявне".
Переноситься як відкрите питання на наступний тиждень.

## Result Week 3 — станом на кінець тижня

- **AI Surfacing Model** — 5 точок, один патерн `Trigger → Loading → Result/Error → Retry → Dismiss`
  усюди, AI ніколи не забирає primary CTA сторінки.
- **Einstein / Bertha / Jupiter concepts** — внутрішня концептуальна модель (Einstein → Changes/Drift,
  Bertha → Failed Scan Troubleshooting, Jupiter → Policies), **повністю підтверджена клієнтом**
  (Stephen Earl, включно з корекцією Felix→Bertha 31.08). Назви strand-ів ніколи не показуються в
  UI — кнопки лишаються generic ("Explain with AI" тощо).
- **AI Interaction Patterns** — спільні правила поведінки: Trigger→Loading→Result/Error→Retry→Dismiss,
  спільний код (`_aiRunPanel`) для 4 з 5 точок, перевірено end-to-end.
- **Roles & Permissions** — матриця сторінка × тип дозволу, без іменованих ролей (свідомо).
- **Visibility & Restrictions** — 4 канонічні стани для обмежених дій, застосовані на 4 сценаріях.

Не працююча функціональна концепція AI-екранів, а модель того, як AI взагалі інтегрується в
Guardian, плюс правила доступу — саме те, що описано в Work Package 2 для Week 3.

## 4. Апдейт того ж дня — Workstream 5 реалізовано в коді (не лише в чаті)

Ранкові пункти 1-3 вище лишились аналізом без правок `index.html`. Після повторного проходу по
Week 3 користувач прямо попросив зупинити цикл «аудит → знову аудит» і **реалізувати
Workstream 5 (Roles, Permissions, Visibility & Restrictions) у коді**, за п'ятьма блоками з
Expected Output оригінального Work Package. Усі п'ять зроблено й перевірено в preview (light +
dark, консоль чиста).

**Нова сторінка `Roles & Permissions`** (сайдбар, `v-roles`, вкладки `Users` / `Roles`) +
**ролевий симулятор** у топ-наві (`Admin · Analyst · Viewer`, той самий принцип, що вже наявний
`app-state-seg`) — перемикає `_currentRole` і одразу перераховує стан реальних сторінок застосунку.

1. **Admin-facing Roles & Permissions.** Таблиця Users (ім'я/email/роль-бейдж/статус/дія) +
   картки трьох ролей (Admin/Analyst/Viewer) з кількістю призначених users.
2. **Assign role + Preview impact.** Клік на «Change role» відкриває канонічну модалку
   (`openModal()`) з `.gm-radio-card` пікером ролі; під ним живий грід «що зміниться» —
   поточна vs нова роль по 5 сторінках (Policies/Drift/Node Detail/Credentials/Schedules),
   кожен рядок = Full access / Read-only / Restricted з кольоровою крапкою. Оновлюється на
   `onchange` радіо, без перезавантаження модалки.
3. **Access states на реальних сторінках** (не вигадані приклади — саме ті 4, що обговорювали
   в п.2 вище):
   - **Hidden** — Node Detail, кнопка «Summarise with AI» (`#nd-ai-dropdown`) зникає повністю
     для Viewer.
   - **Disabled + explanation** — Detected Drift/Change Detail, ряд Approve/Flag/Skip
     (`#cd-exec-row`) дізейблиться разом як один стан, з тултипом чому.
   - **Read-only** — Policy Detail: банер угорі сторінки + Edit/Manage assignment дізейблені
     разом для Viewer (не набір розрізнених сірих кнопок).
   - **Permission required** — Credentials, кнопка «+ New credential» міняє іконку на замок
     для не-Admin і веде не в форму створення, а в Restricted flow (п.4).
4. **Restricted content flow.** `openRestrictedFlow()` — та сама модальна оболонка: банер
   «Restricted — чому» → кнопка «Request access» → підміна вмісту модалки на «Request sent»
   без переходу на іншу сторінку. Підключено до кнопки Credentials з п.3.
5. **Permission review/audit.** На картці кожної ролі — лінк «Who has access? Why?»
   (`openRoleAudit()`): хто має роль зараз + таблиця «що втрачається, якщо роль забрати»
   по тих самих 5 сторінках.

Перевірено в preview: усі 4 access-state на реальних елементах (Node Detail/Detected
Drift/Policy Detail/Credentials) для ролей Admin/Analyst/Viewer, Assign-role impact grid
живий, Restricted flow до confirmation, аудит ролі — все підтверджено значеннями
`getComputedStyle`/`getBoundingClientRect` у світлій і темній темі, консоль без помилок.
Дані (`ROLES`/`USERS`/`PERM_PAGES`) — прототипні масиви в JS, без бекенду, як і решта
застосунку.

**Не входить у цей прохід:** Workstream 3 (Enterprise model, guided layer, reversibility,
recommend/reconcile/prioritise/guide) — окремий, ще не закритий чекліст, чекає паралельно
відповіді Stephen щодо Bertha/Felix + Enterprise tier.
