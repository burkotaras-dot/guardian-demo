# Guardian Interaction Pattern Library

**v1 · Week 2 · 19.08.2026**

14 задач, які повторюються на кожному екрані продукту: Create · Edit · Delete · Configure ·
Test Connection · Mapping · Save · Cancel · Confirmation · Long-running task · Success · Warning ·
Error · Empty State. Кожна — це не новий набір правил, а **рецепт**: які елементи з
`GUARDIAN-INTERACTION-STANDARDS.md` задіяні разом, коли розробнику треба зібрати одну конкретну
задачу, а не читати весь документ.

Три документи, три різні питання:

| Документ | Питання | Одиниця |
|---|---|---|
| `GUARDIAN-DESIGN-SYSTEM.md` | як це виглядає | компонент |
| `GUARDIAN-INTERACTION-STANDARDS.md` | як поводиться один елемент | правило |
| `GUARDIAN-PATTERN-LIBRARY.md` (цей файл) | як зібрати одну задачу з готових елементів | патерн |

**Ця бібліотека нічого не визначає заново.** Кожен патерн нижче — це посилання на конкретні
правила Standards + один реальний екран, що їх реалізує. Якщо число, колір чи лейбл потрібні —
вони в Standards/Design System; тут лишається тільки композиція. Дублювання значень у двох місцях —
саме та проблема, яку розділ 15 Standards уже задокументував один раз; цей файл її не повторює.

Формат кожного патерну — пʼять частин:

- **Behaviour** — що відбувається і чому саме так.
- **Layout** — з яких блоків зібраний екран.
- **Actions** — які контролі є і як називаються.
- **States** — які стани проходить.
- **Edge cases** — що йде не за планом і як це показано.

## 1. Create

**→ Standards** §1.1 · §2 (Wizard) · §5.2 · §6.3

**Behaviour.** Будь-яке Add / Create / Connect відкриває overlay-модалку через `openModal()`,
ніколи окремий full-page екран (§1.1). Проста сутність — одна стадія; сутність, що потребує
конфігурації чи перевірки підключення (нода, інтеграція) — багатостадійний wizard (§2).

**Layout.** `gm-overlay` → `gm-card` → `gm-head` (+ `gm-stepper`, якщо стадій більше однієї) →
`gm-body` → `gm-foot`. Для одностадійного create степпера немає взагалі — не «степпер з одним
кроком», а його відсутність.

**Actions.** Праворуч у футері — Primary, лейбл називає результат: «Add node», «New credential» →
`Save credential`. Ліворуч — `Cancel` (одностадійно) або `Back` (перша стадія wizard, § 2.5).

**States.** Порожня форма (Primary активний — валідація в модалці за клацанням, §13.1, не
disabled-submit) → заповнена → invalid (червона рамка на невалідних полях при спробі сабміту) →
`loading` на Primary під час запиту → створено.

**Edge cases.** Форму із введеними даними закриває лише `confirmDirty` (§6.2/§6.3), а не
мовчазний Esc. Один код-шлях для Create і Edit — реальний приклад: `openCredEditModal(c)` рендерить
той самий `#cred-edit-overlay`, і лише заголовок/лейбл Primary міняються за `c ? 'Edit' … : 'New' …`
(`index.html:13803`). Тест підключення (`Test credentials`) живе в `footerLeftHtml` тієї ж форми —
це вхідна точка в патерн §5 Test Connection, а не окрема сторінка.

## 2. Edit

**→ Standards** §3.3 · §1.2 · §5.2 · §6.3

**Behaviour.** Редагування відбувається **там, де сутність живе** — не повторним проходом
wizard'а створення (§3.3). Full-page і overlay мають різне шасі, і воно фіксоване.

**Layout.**

| Контейнер | Ліворуч | Праворуч | Cancel |
|---|---|---|---|
| Full-page | `.back-btn` (§1.2) | `Save changes` | немає — back і є ним |
| Overlay | — | `[Cancel, Save changes]` у `gm-foot` | є |

**Actions.** Лейбл Primary завжди «Save changes» (§5.2) — не «Apply», не «Update», не «OK»:
слово описує, що станеться, а не де ти опинився.

**States.** clean (Primary активний, ідемпотентний) → dirty → invalid → `loading` → saved
(тихе підтвердження — §14.2 — або toast «<Сутність> updated», §10.3).

**Edge cases.** Дубльований `Cancel` поруч із back на full-page — порушення §5.1/§3.3, не існує
в policy-edit/policy-assign. Inline-перейменування одного поля не має ані back, ані «Save changes»:
Enter зберігає, Esc скасовує (§3.3 exception) — це найменший можливий Edit, без модалки і без
футера взагалі.

## 3. Delete

**→ Standards** §6.3 · §8.4

**Behaviour.** Підтвердження вимагає **persisted-сутності**. Незбережений під-елемент форми
(тег, рядок) видаляється миттєво без питання — саме тому Delete і Cancel незбереженого чернетки
не плутаються.

**Layout.** `openModal` size `sm`. Якщо видалення має видимий наслідок для інших обʼєктів —
imapct preview зверху тіла (§8.4): «скільки нод залежать від цього credential».

**Actions.** `[Cancel, <Дієслово> (destructive)]`. Дієслово називає сутність: «Delete policy»,
не «OK», не голий «Delete».

**States.** default confirm → (опційно) warning-варіант з impact preview → `loading` на
destructive-кнопці → видалено (toast «<Сутність> deleted»).

**Edge cases.** Дія з доступним undo (§14.1) обходиться без модалки — undo замінює підтвердження,
не доповнює його. Persisted-сутність без підтвердження — дефект: `deleteSavedView` мав саме цю
діру, закрито 13.08.2026. `window.confirm()` заборонено в принципі (§6.3) — увесь Delete у продукті
йде через кастомний `confirmDiscard`-подібний діалог.

## 4. Configure

**→ Standards** §3.4 (Progressive disclosure) · §1.3

**Behaviour.** Задача відрізняється від Create тим, що сутність вже існує — користувач обирає
**обсяг і параметри** операції над нею, а не саму сутність. Система не робить широкий незворотний
вибір за користувача (§3.4): кожен параметр видимий і редагований, а не прихований за замовчуванням.

**Layout.** Секції за змістом (`form-label` + `gm-radio-group`), не плаский список: «Compliance
Policy Level», «Scope», «Schedule». Підопції розкриваються лише коли вибрано батьківський радіо
(`:has(input:checked)` у CSS, без JS-обробника) — приклад: вибір «By node type» у
`openAwsScanConfigModal` (`index.html:26385`) розкриває чекбокс-список EC2/RDS/EKS/ECS. Контекстна
підказка (`gm-info-note`) поруч із вибором, що впливає на продуктивність; оцінка часу — окремим
рядком перед дією, що запускає операцію.

**Actions.** Back веде на попередню стадію, не втрачаючи вибір (§2.5) — Configure типово є однією
зі стадій довшого флоу, а не самостійною модалкою. Primary називає результат операції («Start Scan»),
не саму дію «Configure» чи «Save».

**States.** Безпечний варіант обраний за замовчуванням і позначений («Level 1 · recommended»);
розширений вибір (by node type) — окремий стан з підсписком; підсумковий рядок з оцінкою часу
з'являється лише коли вибір завершено.

**Edge cases.** Це не окрема модалка з власною ідентичністю — `openAwsScanConfigModal` малює
той самий `#aws-connect-overlay` і той самий `gm-stepper` із трьома стадіями, що й решта AWS-флоу
(§2.7 Side Panel: контекст не зникає). Новий Configure-екран **не** отримує окремий заголовок
поза степпером батьківського флоу.

## 5. Test Connection

**→ Standards** §2.8 · §2.9 · §11.2 · §8.3

**Behaviour.** Перевірка виконується **всередині поточної стадії**, ніколи не переходом на нову
сторінку. Показується покроковий чекліст, а не один спінер (§11.2 — багатоетапна операція).

**Layout.** Список `.agentless-test-row`, по одному рядку на перевірку (доступність хоста,
автентифікація, права). Кожен рядок несе власну іконку стану.

**Actions.** Primary («Test connection & continue») блокований, поки перевірка не пройде. При
відмові поруч з'являється secondary `Retry test` — не заміняє Primary, а стоїть поряд із ним
(§2.9).

**States.** not-run → running (чекліст оновлюється по рядку) → pass (Primary розблоковано) →
partial-fail / fail (Retry видимий, Primary заблокований).

**Edge cases.** Повтор переграє **той самий** сценарій на місці — `agentlessTestRetry()` бере
`ov._agentlessTestKey` і не скидає вже введені Target/Credentials (§8.3: відкидати на початок флоу
заборонено). ⚠️ Відомий, ще не закритий дефект термінології: лейбл кнопки «Test Connection» на
одному екрані та «Test connection & continue» на іншому (§2.4, розходження #2 з `guardian-wizard-pattern.md`).

## 6. Mapping

**→ Standards** §3.4 · §2.9 · §13.1

**Behaviour.** Тристадійний флоу, що живе в межах однієї стадії батьківського wizard'а —
Select fields → Configure mapping → Review & activate (`_FM_MODAL`, `index.html:12380`).
Обов'язкові поля обрані й заблоковані заздалегідь; необов'язкові — явний вибір користувача (§3.4);
поля поза мапінгом сховані під розкривний «N skipped fields», не видалені.

**Layout.** Панель-статусбар над таблицею: кількість обраних / обов'язкових / опційних із
кольоровими крапками (та сама граматика, що severity-дот, §7.3, але тут — лічильник, не severity).
Рядок таблиці на кроці 2: source field → mapped-to (`.fm-guardian`) → transform (dropdown) →
default value → статус.

**Actions.** `Test mapping` (secondary) валідує всі рядки одразу; Primary «Next: Review & activate»
розблоковується лише після проходження. Будь-яка зміна трансформації чи default value **скидає**
результат тесту (`_fmResetTest`) — застарілий «Pass» ніколи не переноситься на змінений мапінг.

**States.** На рівні рядка: Not tested → Pass / Warning / Conflict / Error. Conflict — коли два
джерела мапляться в одне поле Guardian; під рядком з'являється пояснювальний рядок з переліком
конфліктуючих полів (не toast, не модалка — §13.1: помилка лишається біля причини).

**Edge cases.** Error на рівні рядка блокує Primary кроку, але не скидає вибір усього кроку —
це object-level retry (§2.9): виправляється один рядок, решта мапінгу лишається як є. ⚠️ Статус
рядка (`.fm-validation`) — саморобний inline-варіант, не `.bdg` (§7.1 каже: статус несе один
компонент). Вартий звірки при наступній консолідації баджів, окремо не чіпається цього тижня.

## 7. Save

**→ Standards** §3.3 · §5.2 · §10.3

**Behaviour.** Save фіксує поточний стан форми **без виходу з контексту** — на відміну від
`Done`, яке лише закриває вже збережене (§5.2).

**Layout.** Primary завжди останній елемент у `gm-foot-right` або в правому верхньому куті
full-page хедера (§5.1).

**Actions.** Лейбл — рівно «Save changes». «Apply», «OK», «Submit» не використовуються ніде
в продукті (§5.2) — вони не кажуть, що станеться.

**States.** dirty (Primary активний) → `loading` → saved. Повідомлення про результат —
`<Сутність> <дієслово в past tense>`, без «successfully», без крапки: «Assignment saved»,
не «Policy saved successfully» (§10.3).

**Edge cases.** Inline-перейменування одного поля обходиться без кнопки Save взагалі — Enter
є збереженням (§3.3 exception). Це найменший можливий Save-патерн: жодного футера, жодної модалки.

## 8. Cancel

**→ Standards** §6.2 · §1.2 · §5.1

**Behaviour.** Три способи закриття (`gm-x`, backdrop, `Esc`) проходять через **один** обробник —
`requestClose()`. Full-page не має окремого Cancel поруч із Back: Back і є скасуванням (§1.2/§3.3).

**Layout.** У модалці — `Cancel` ліворуч від Primary в `gm-foot-right`. У full-page — `.back-btn`
32×32 у верхньому лівому куті, з явною білою заливкою на світлій темі (не `transparent`, §1.2).

**Actions.** Лейбл модального Cancel — рівно «Cancel», ніколи «Close» для форми з незбереженим
вводом (Close має інше значення — завершено й нема що втрачати).

**States.** clean → закривається миттєво. dirty → `confirmDirty` (§6.2) перехоплює закриття.

**Edge cases.** Саме тут жили два з шести відхилень еталонного Add Node wizard'а — `agentless-setup-overlay`
і `aws-connect-overlay` не передавали `confirmDirty`, і Esc мовчки стирав заповнену форму.
**Виправлено 19.08.2026** (обидві форми зараз питають перед закриттям із введеними даними).

## 9. Confirmation

**→ Standards** §6.3

**Behaviour.** Той самий механізм, що й Delete (§3 вище), але не обов'язково destructive:
підтвердження запускається для будь-якої дії, наслідок якої не очевидний і його важко скасувати.

**Layout.** `openModal` size `sm`, ті самі два контролі: [нейтральна відмова, дієслово-дія].

**Actions.** Дієслово називає дію («Discard changes», «Delete policy»), ніколи «OK»/«Yes».
Нейтральна відмова — «Cancel» (не «No»).

**States.** shown → confirmed / dismissed. Проміжного стану немає — це модальна пауза, не флоу.

**Edge cases.** Канонічний приклад — `confirmDiscard()`: `[Keep editing, Discard changes]`.
`window.confirm()` більше не використовується ніде в продукті (закрито 12.08.2026) — єдиний
нативний браузерний діалог у повністю кастомній модальній системі був сам по собі порушенням
цього патерну.

## 10. Long-running task

**→ Standards** §11.1 · §11.2 · `long-running-operations.md`

**Behaviour.** Операція довша ~2с показує, **що саме відбувається**, не факт очікування.
Довша ~10с додає вихід без скасування — «Continue in Background» — і каже, де з'явиться результат.

**Layout.** Чекліст етапів (пройдені з галочкою, поточний активний, майбутні тихі) АБО прогрес-бар
з підписом обсягу («7 of 12 nodes complete · Est. 3 min remaining») + node-by-node статус
(`openAwsScanningModal`, `index.html:26441`).

**Actions.** Одна Primary — сам вихід («Continue in background»), не Cancel операції.

**States.** running → (по кожному вузлу) done / run / wait → complete / failed.

**Edge cases.** ⚠️ ВІДКРИТО, блокує остаточний текст: `openScanningModal` пише «Do not close this
tab», `openAwsScanningModal` того ж класу операції дає «Continue in background» — дві протилежні
відповіді на одне питання «чи можна піти». Формулювання свідомо не уніфіковано, поки не прийде
відповідь від Connor на OQ-10 (Standards §16) — обіцяти фонове виконання, не знаючи, чи бекенд
його справді підтримує, означає закодувати здогадку як стандарт.

## 11. Success

**→ Standards** §14.2 · §14.3

**Behaviour.** Ієрархія тиші (§14.2): зміна на екрані сама по собі → toast `success`, якщо
результат не видно → повний success-екран лише для завершення багатокрокового флоу.

**Layout.** Коло 56×56, ghost-green фон `rgba(37,167,96,0.1)`, SVG-галочка 24–28px
`stroke #25A760`, заголовок 20px/800 без знаку оклику, підзаголовок, опційна міні-статистика,
CTA — filled `btn-primary`.

**Actions.** Рівно одна CTA у футері — і вона веде **кудись**, не просто закриває (§2.11 Finish
для wizard-варіанта цього патерну).

**States.** Це термінальний стан — станів усередині немає.

**Edge cases.** Незворотні або дорогі операції (видалення інтеграції, імпорт сотень нод) можуть
отримати повний success-екран навіть поза багатокроковим флоу — користувачеві потрібне однозначне
підтвердження завершення, тихого стану тут недостатньо.

## 12. Warning

**→ Standards** §8.4

**Behaviour.** Стан, що **не блокує**, але змінює рішення користувача до того, як він діє —
не після. «Дія спрацює, але наслідок може бути не той, якого очікуєш».

**Layout.** Inline-блок у тілі форми/модалки, **до** контролю дії, якого стосується.

**Actions.** Warning не має власної дії — він лише декорує дію, яку описує (найчастіше
destructive-Primary в Confirmation/Delete).

**States.** присутній (є залежні обʼєкти) / відсутній (залежностей немає, підтвердження без
warning-блоку).

**Edge cases.** Успішний результат із застереженням («Imported 8 of 10») — це **info** з
деталізацією, не warning: warning міняє рішення до дії, info лише повідомляє після. Еталон —
impact preview в `credDelete`: «скільки нод залежать від цього credential» перед видаленням.

## 13. Error

**→ Standards** §8.1 · §8.2 · §8.3 · §13.1

**Behaviour.** Завжди червона семантика + завжди шлях відновлення. Носій обирається за
масштабом — поле, дія, крок флоу чи вся сторінка (§8.1).

**Layout.**

| Масштаб | Носій |
|---|---|
| Поле форми | inline під полем (`vFormError`, §13.1) |
| Дія на екрані | toast `error` (§14.1) |
| Крок флоу | inline-блок у місці кроку + кнопка retry |
| Сторінка недоступна | ghost-red коло + SVG circle-info + «N errors found» + «Try again →» |

**Actions.** Текст називає причину **і** наступну дію. «Something went wrong» без дії — тупик,
не помилка.

**States.** field-invalid → step-failed → (при повторі) recovering → recovered / page-error.

**Edge cases.** Повтор завжди відбувається **на тому самому місці**, де сталась помилка (§8.3) —
відкидання на початок флоу заборонено, крім сесії, що справді протухла (тоді про це сказано явно).
Історичний дефект, закритий 12–13.08.2026: пʼять помилок валідації показувались у **зеленому**
success-toast з галочкою — найгрубіше порушення колірної семантики в продукті на той момент.

## 14. Empty State

**→ Standards** §9.1

**Behaviour.** Порожній список ніколи не буває просто порожнім рядком тексту. Два типи причини,
і кожна веде до іншої дії.

**Layout.** icon-circle 44×44 + заголовок 14px/600 + підпис 12px + дія — клас `.es` (`.es-sm` у
компактній панелі). Жодних нових CSS-значень для нового порожнього стану не потрібно.

**Actions.**

| Тип | Причина | Дія |
|---|---|---|
| no-match | фільтр/пошук нічого не знайшов | reset-посилання «Clear filters» |
| true-empty | сутностей не існує взагалі | filled `btn-primary` CTA, що створює першу |

**States.** По суті сам є станом (порожнім) списку/таблиці/панелі — не переходить у щось інше,
доки дані не з'являться.

**Edge cases.** Reset без обробника — не reset: `ndResetAttrFilters()` чистить одразу пошук і
статус-фільтр. Порожній стан у dropdown/поповері обмежується одним рядком тексту — icon-circle
44×44 у контейнері 240px непропорційний (виняток — `recon-node-empty`). Порожня комірка в
заповненому рядку («—») empty state не є.
