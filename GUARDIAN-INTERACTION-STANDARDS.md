# Guardian Interaction Standards

**v1 · Week 2 · 17.08.2026**

Єдина мова взаємодії Guardian. Документ відповідає на одне питання: **як продукт поводиться** —
коли питає, коли повідомляє, коли показує прогрес, як називає дії, що робить при помилці.

Мета не «описати стандарти», а зняти потребу вигадувати. Будь-який новий Wizard, Table, Modal
або Form не проєктується з нуля: дизайнер відкриває цей документ, бере готовий патерн, розробник
реалізує його без окремої UX-дискусії.

---

## Як читати

Кожне правило складається з **чотирьох** частин:

- **Rule** — що є стандартом.
- **Reference** — один еталонний екран/компонент. Один, не список.
- **Examples** — де застосовано коректно; де порушено.
- **Exceptions** — коли правило можна порушити і чому.

Якщо екран не відповідає правилу і не підпадає під зафіксований Exception — він неправильний.

**Позначки статусу розділу:** ✅ повний · 🟡 чернетка, поглиблюється цього тижня · ⏳ порожній.

## Спільний принцип

**Однакові дії поводяться однаково.** Якщо два екрани виконують дію одного класу, користувач
отримує ту саму відповідь, тими самими словами, у тому самому місці екрана.

Практичний наслідок для пріоритизації: правило, що діє на 30 місць, важливіше за дефект,
що видно на одному екрані.

## Action Hierarchy

Базовий принцип, вищий за розділ Buttons: він вирішує, **яка дія головна**, тоді як §5 вирішує,
**як вона виглядає й де стоїть**.

**Rule.** Primary CTA відображає **поточну мету користувача в поточному контексті**, а не
верстку сторінки. Один і той самий екран або компонент може мати різні primary-дії залежно від
етапу роботи.

**Reference.** Клієнт, Slack-тред 18.08.2026 — правило сформулювали двоє незалежно
(Gareth Brown, hamish): *Run Simulation is the primary action when you're building/editing…
Export is the primary action when you're viewing…*

**Examples.**
- Policy Edit / Policy Create → primary = **Run Simulation**, Export вторинний.
- Policy Results → primary = **Export**, Run Simulation вторинний.
- Наслідок для верстки: **позиція primary не змінюється** (§5.1) — змінюється лише те,
  яка з кнопок несе акцент.

**Exceptions.** Наразі не визначено.

Правило не обмежене Reports: воно так само поширюється на wizard-и, Integrations, Policies,
Drift та будь-який екран, що має більш ніж один етап роботи.

# 1. Navigation

## 1.1 Вхід у створення — overlay modal

**Rule.** Будь-яка дія класу **Add / Create / Connect / Import** відкриває **overlay-модалку**
через `openModal(opts)`. Окремих full-page екранів створення не існує.

Причина зафіксована клієнтом: Gareth Brown (27.07.2026) перелічив чотири різні шасі створення
в одному продукті й прямо назвав overlay своєю преференцією («Like Flow»).

**Reference.** `openModal(opts)` — уніфіковане шасі: `gm-overlay` / `gm-card` / `gm-head` /
`gm-stepper` / `gm-body` / `gm-foot`.

**Examples.**
- ✅ Policy Create (`pc-wizard`), CM Group (`cm-wizard`), Add Check (`ac-wizard`), Field Mapping,
  New Credential, Integration Connect (`icx-wizard`).
- ✅ Add Node (Figma `3165:10694`) — модальне шасі 600px із чотирикроковим `gm-stepper`
  Add node → Connect → Scan → Results.

**Exceptions.** `v-s-agentless` — повноекранний онбординг одного вузла. Виняток свідомий:
багатосекційна первинна конфігурація, яку неможливо стиснути в 600px без втрати контексту.
Виняток **один**; новий full-page create потребує окремого рішення.

## 1.2 Back

**Rule.** Повернення на full-page екрані — **icon-only `.back-btn` 32×32** угорі ліворуч.
Саморобних текстових `← Back` не існує. Handler — `navBack()`.

На світлій темі кнопка має явну білу заливку (`var(--bg-surface)`), не `transparent` — інакше
зливається з полотном `--bg-canvas`.

**Reference.** `.back-btn` + `navBack()`.

**Examples.**
- ✅ policy-edit, policy-assign — лівий back, без дубльованого правого `Cancel`.
- ❌ `j3-results` — текстова `btn-outline ← Back` замість канонічної.

**Exceptions.** Текстові хлібні крихти (`.back-link`) свідомо безрамкові й під правило не підпадають.

## 1.3 Повернення з режиму перегляду

**Rule.** Екран, відкритий **лише для перегляду**, повертає туди, звідки його відкрили — а не
в середину флоу, якого користувач не проходив.

**Reference.** `j3ResultsBack()`.

**Examples.**
- ❌ Клієнтський баг (Gareth, 27.07.2026): `Integrations → AWS → View Details` перевикористовує
  `j3-results` у режимі `_awsDetailMode`; `Back` веде на непоказані сторінки майстра, єдиний вихід
  із чистого перегляду — `Cancel`.

**Exceptions.** Немає. Read-only вхід не має виводити в write-флоу.

# 2. Wizard Navigation

> 🟡 **Розділ поглиблюється у вівторок.** Нижче — шасі, підтверджене розробкою. У вівторок
> додаються правила по кожному елементу: Stepper · Stage Indicator · Next · Back · Exit ·
> Side Panel · Progress · Retry · Validation · Finish, і Figma отримує Reference Wizard.

Це найбільша тема входу розробки. Connor Conway (GWB-6638 §5) прямо пише: питання не про один
флоу, а про **патерн, який визначить кожен наступний майстер**. Позиція розробки — реалізація вже
правильна, просять зафіксувати її як стандарт. Bambuk погодився з усіма пʼятьма пунктами
12.08.2026.

## 2.1 Wizard chrome — пʼять правил

**Rule.**

1. **Індикатор стадій не містить під-стадій.** Під-стадія робить індикатор недостовірним — він
   перестає казати, де ти. *(DEC-1)*
2. **`Next` завжди рухає індикатор на наступну стадію.** Кнопка, що відкриває новий екран,
   лишаючи індикатор на місці, ламає очікування, яке цей індикатор задав. *(DEC-2)*
3. **Ліва панель і номер стадії присутні на всіх стадіях.** Зникнення панелі на середині
   читається як вихід із флоу. *(DEC-3)*
4. **`Back` завжди top-left, в одному стилі** (§1.2). Навігація не рухається між кроками одного
   флоу. *(DEC-4)*
5. **Кожен екран флоу — нумерована стадія.** Сторінок поза нумерацією, з яких немає вороття,
   не існує. Помилка виправляється **всередині стадії**, без виходу з неї. *(DEC-5)*

**Reference.** Флоу підключення AWS у реалізації GWB-6638 — три стадії
**Connect AWS · Node Discovery · Node Inventory**, верифіковано end-to-end на реальному акаунті.

**Examples.**
- ✅ Stage 1 «Connect AWS» розділено на нумеровані секції: що вводить користувач / що генерує
  Guardian / верифікація (CN-09). Єдиний ввід клієнта — 12-значний account ID.
- ✅ Кожна картка на Integrations відкриває сторінку **свого** акаунта, тому delete застосовується
  до правильного (CN-14).
- ❌ Прототип `#j3-step-nav` — чотири вайрфреймові стадії замість трьох (§10.1); саморобна
  текстова `← Back` на `j3-results` замість `.back-btn`.

**Exceptions.** Overlay-майстри використовують `gm-stepper` і `Back`/`Next` у `gm-foot` замість
лівої панелі та `.back-btn`: правила 1, 2, 5 діють без змін, правила 3 і 4 замінюються
еквівалентами модального шасі (§2.2, §6.2).

## 2.2 Stepper

**Rule.** Один stepper на флоу. У модалці — `gm-stepper` через опцію `steps` в `openModal`;
паралельного full-page step-nav поруч не існує.

Кількість кроків у stepper дорівнює кількості реальних стадій. Стадія, якої немає в stepper,
не існує. Лічильник кроку в бейджі дорівнює кількості кроків у навігації.

**Reference.** `gm-stepper` в Add Node: Add node → Connect → Scan → Results.

**Examples.**
- ✅ `icx-wizard` — full-page `icx-step-nav` вимкнено (`display:none`), лишився модальний stepper.
- ❌ `#j3-step-nav` — `Node Inventory` у stepper відсутній узагалі, id-нумерація рвана
  (`j3-si2` немає).

**Exceptions.** Немає.

## 2.3 Ще не написано

Вівторок: **Stage Indicator · Next · Back · Exit · Side Panel · Progress · Retry · Validation ·
Finish** — по одному правилу на елемент, у форматі Rule · Reference · Examples · Exceptions.
Паралельно — Reference Wizard у Figma, щоб правило мало візуальний еталон, а не лише текст.

# 3. Forms

> 🟡 Поведінкова частина. Візуальні значення полів — у Design System §3.

## 3.1 Заливка поля

**Rule.** Поле вводу на картці або панелі **не може** мати колір самої картки — інакше воно
не читається як поле. Еталон — модалка «New credential».

- **Light:** `var(--bg-subtle)`; фокус → `var(--bg-surface)`.
- **Dark:** `rgba(255,255,255,0.05)`, бордер `rgba(255,255,255,0.2)`; фокус → `rgba(255,255,255,0.07)`
  + зелений бордер.

У dark **не** використовувати `var(--bg-subtle)` для полів: воно темніше за картку і виглядає
запалим.

**Reference.** `#cred-edit-overlay` — `.csel-btn` / `input.form-input`.

**Examples.** ✅ `.form-input`, `.icx-input`.

**Exceptions.** Немає. Задається CSS-класом, ніколи inline: `_syncInlineTheme` мутує інлайнові фони.

## 3.2 Фокус

**Rule.** Будь-яке текстове поле, включно з інлайновими полями пошуку, при фокусі дає той самий
сигнал: зелений бордер + кільце `0 0 0 3px var(--green-dim)`.

**Reference.** `.form-input:focus`.

**Examples.** ✅ 7 інлайн-полів пошуку уніфіковано 07.08.2026.

**Exceptions.** Немає.

## 3.3 Edit / save

**Rule.** Шасі редагування визначається контейнером і воно фіксоване:

| Контейнер | Ліворуч | Праворуч | Cancel |
|---|---|---|---|
| **Full-page edit** | `.back-btn` (§1.2) | `Save changes` | **немає** — back і є скасуванням |
| **Overlay-модалка** | — | `[Cancel, Save changes]` у `gm-foot` | є |

Дубльований `Cancel` поруч із back на full-page — надлишковий контрол (порушує §5.3).
Незбережені зміни при виході → підтвердження за §6.3.

Редагування наявної сутності відбувається **там, де вона живе** — не через повторний прохід
майстра створення. Якщо сутність налаштовується майстром, її сторінка керування має ті самі
секції, що й майстер, і дозволяє перевірити зміну на місці (retest).

**Reference.** Сторінка керування AWS-інтеграцією (CN-13) — scan config, retest і delete в одному
вікні, тим самим чеклістом, що й у майстрі.

**Examples.** ✅ policy-edit, policy-assign — стандартизовано 31.07.2026.

**Exceptions.** Inline-перейменування одного поля не має ані back, ані `Save changes`:
Enter зберігає, Esc скасовує.

## 3.4 Progressive disclosure

**Rule.** Система не робить широкий незворотний вибір за користувача. Там, де операція має обсяг
(що сканувати, що імпортувати, які ноди брати під керування), користувач **обирає явно**,
а не отримує «все» за замовчуванням.

Вибір подається **згрупованим за змістом**, не пласким списком, показує лічильник обраного
і пояснює, що станеться з **необраним**.

**Reference.** Node Discovery (CN-07) — типи ресурсів згруповані за сервісом (Compute / Database /
Storage / Identity & Security / Networking / Management & Monitoring), лічильник `2/4`,
`Select all` на групу. Необране лишається під **Detected Nodes**.

**Examples.**
- ✅ Node Inventory — перелік знайденого з фільтром за типом і per-item вибором (CN-11).
- ✅ CM-picker в agentless-онбордингу — фільтрація за сумісністю протоколів замість повного списку.

**Exceptions.** Обовʼязкові технічні передумови (регіони, без яких флоу не працює) можуть бути
попередньо вибрані — але лишаються видимими й редагованими.

# 4. Tables

> 🟡 Поведінкова частина. Візуальні значення — Design System §4.

## 4.1 Заголовок і hover

**Rule.** Рядок заголовків колонок у dark — `#063135`, ніколи чорний. Hover рядка не змінює
семантику: це лише підсвітка, не стан.

**Reference.** `body.dark .data-table th` + спільний клас `.col-thead`.

**Examples.** ✅ `.drift-thead`, `.j3-table th`, `.compare-thead` уніфіковано 21.07.2026.

**Exceptions.** Немає.

## 4.2 Таби та сегментовані контроли

**Rule.** Це **два різні компоненти**. Вибір робиться не за виглядом, а за тим, що перемикається:

| Компонент | Коли | Ознаки |
|---|---|---|
| **Таби** (`.pol-tab`) | перемикають **фільтр-вимір сторінки**: взаємовиключні зрізи одного списку, у кожного свій обсяг | підкреслення активного + **лічильник у баджі** |
| **Сегментований контрол** (`.seg` / `.seg-btn`) | перемикає **режим або джерело** всередині тулбару; обсяг не показує | одна зʼєднана доріжка, **без лічильників** |

Сегментований контрол — це ОДНА доріжка. Окремі плаваючі пігулки сегментованим контролом не є.
`.toggle-group` — форм-варіант того самого контролу.

JS **не фарбує** сегменти інлайн — лише `classList.toggle` + `aria-pressed`.

**Reference.** Сегмент — `#node-filter-btns` (All / Local / AWS). Таби — `#results-pills`.

**Examples.**
- ✅ 12.08.2026 пʼять незалежних реалізацій зведено до однієї: 7 доріжок / 17 сегментів.
- ✅ Detected Drift — фільтр-вимір із лічильниками, тому **таби**.
- ❌ Колір активного таба в dark заданий лише для `.remed-tabs`; решта успадковують `#059669` —
  низький контраст на темному полотні.

**Exceptions.** Таб без лічильника допустимий, якщо обсяг неможливо порахувати дешево.
Зворотне — сегмент із лічильниками — ні: лічильник є ознакою табів.

## 4.3 Ще не написано

Сортування · пагінація · bulk-виділення й тулбар масових дій · поведінка при 120+ рядках.
Останнє має вхід від клієнта (Zakk, 12.08.2026): consensus / compare-nodes не масштабуються,
клієнт просить повернути heat map. Питання конкурує зі скоупом пакета — див. §16.

# 5. Buttons

> Візуальна специфікація — Design System §6.5 (шість канонічних типів з Figma). Тут — коли який
> тип, де стоїть і як називається. **Яка саме дія є головною** — вирішує Action Hierarchy вище.

## 5.1 Розміщення та порядок

**Rule.** Головна дія — **праворуч**, вторинні — ліворуч від неї, у тому самому ряду.
Порядок: `[вторинні …, головна]`, головна завжди остання. Дві головні дії в одному ряду
не існують.

- **Overlay-модалка:** Back — у `.gm-foot-left`, основна група — у `.gm-foot-right`.
  `Cancel` або supportive secondary стоїть ліворуч від Primary.
- **Full-page:** головна дія праворуч у хедері, навігація назад — ліворуч (§1.2).
- Destructive займає позицію головної, але з `kind:'destructive'`.

Дозволені рівно чотири композиції footer: (1) одна Primary праворуч; (2) Back + Primary;
(3) Back + supportive Secondary + Primary; (4) лише Back.

**Reference.** `openModal` → `.gm-foot`; кнопки рендеряться в порядку масиву `opts.buttons`.

**Examples.**
- ✅ Усі перевірені call-sites дотримуються `[Cancel/secondary, …, primary/destructive]`.
- ⚠️ `openModal` приймає довільний `buttons[]` і **не валідує порядок** — правило тримається на
  дисципліні. При додаванні нової модалки звіряти явно.

**Exceptions.** Toolbar над таблицею і row-level actions — не footer-дії, живуть за §5.4.

## 5.2 Лейбли термінальних дій

**Rule.** Слово на кнопці описує, **що станеться**, а не де ти в інтерфейсі:

| Лейбл | Коли | Що робить |
|---|---|---|
| **Save changes** | редагування наявної сутності | зберігає, лишає в контексті |
| **Done** | завершення флоу, де вже все збережено | лише закриває |
| **Confirm** | підтвердження вибору перед виконанням | фіксує вибір, далі йде дія |

Не використовувати «Apply», «OK», «Submit» — вони не кажуть, що станеться.

**Reference.** Policy Edit — `Save changes`.

**Examples.**
- ✅ policy-edit, policy-assign, edit-check.
- ⚠️ «Done» у CM wizard finish і CI picker — перевірити, що там справді нічого не зберігається.

**Exceptions.** Доменні дієслова сильніші за загальні: «Reconcile», «Approve», «Disconnect»,
«Run scan» лишаються як є.

## 5.3 Один результат — один контроль

**Rule.** Два контролі, що ведуть до одного результату, поруч не ставляться — користувач обере
не той. Якщо на кроці вже є «Continue», окремий «Skip» **не потрібен**: Continue має проходити
далі й без вибору.

Вихід із флоу і пропуск кроку — **різні** дії й не називаються одним словом (§10.2).

**Reference.** Node Inventory у GWB-6638 — Skip прибрано, Continue проходить далі з порожнім
вибором. Обґрунтування розробки: *«two controls for one outcome invite the wrong one»* (CN-12).

**Examples.**
- ❌ «Skip for now» поруч із «Continue to Scan Setup», причому Continue веде на наступну стадію,
  а Skip викидає на dashboard. Різні наслідки, схожі лейбли.

**Exceptions.** Справді необовʼязковий крок може мати явний пропуск — але тоді на кроці **немає**
окремого Continue: пропуск і є проходженням далі.

## 5.4 Кнопка дії в рядку або смузі

**Rule.** Будь-який рядок списку чи смуга-картка з кнопками дії (`View`, `Edit`, `Review`,
`Reconcile`, …) використовує канонічний **`Secondary`** — єдиний тип для цього патерну app-wide.
Власних кольорів це правило не задає.

Новий рядок-із-кнопкою не потребує **жодного** нового CSS. Скоупити під клас рядка можна лише
**геометрію**; колір, розмір і стани перевизначати заборонено. Ніколи inline.

**Reference.** Бази `.btn-secondary` і `.action-cta`. Зразок — Dashboard → «Needs your attention».

**Examples.**
- ✅ 12.08.2026 застосунок переведено за один прохід: **54** екземпляри дають ОДНУ computed-сигнатуру
  в кожній темі.
- ⚠️ Інлайнові `font-size` / `padding` переважують канон — при міграції знято ~49 таких атрибутів.

**Exceptions.** Destructive row-action (`Disconnect`) зберігає червону семантику. Icon-only
overflow-меню — це `Only icon`, не кнопка дії в рядку.

# 6. Dialogs

## 6.1 Контент модалки безрамковий

**Rule.** Контент лежить безпосередньо на `gm-body`. Вкладених «карток-рамок» усередині модалки
не існує: модалка вже є рамкою, друга рамка створює хибну ієрархію.

**Reference.** `gm-body`.

**Exceptions.** Виділений блок-акцент усередині модалки (напр. смуга «що ми знайшли» в Add Node)
допустимий — це не картка контенту, а носій одного твердження плюс дія над ним.

## 6.2 Закриття

**Rule.** Модалка закривається трьома способами, і всі три обовʼязкові: `gm-x` (×),
клік по backdrop, `Esc`. За наявності незбережених змін кожен із них проходить через
підтвердження (`confirmDirty`).

**Reference.** `requestClose()` в `openModal`.

**Exceptions.** Модалка, що показує незавершену операцію (виконується імпорт), може бути
non-dismissable — але тоді має явну дію «Continue in Background» (§11).

## 6.3 Confirmation

**Rule.** Підтвердження вимагають **persisted-сутності**. Під-елементи ще незбереженої форми
видаляються миттєво, без питання.

| Що видаляється | Підтвердження |
|---|---|
| Збережена сутність (policy, credential, node group, saved view, інтеграція) | **так** — модалка |
| Тег / рядок / елемент усередині незбереженої форми | **ні** — миттєво |

Діалог підтвердження — завжди `openModal` size `sm`, кнопки `[Cancel, <Дієслово> (destructive)]`.
Дієслово називає дію («Delete policy»), не «OK». Де наслідок неочевидний — додається
impact preview (§8.4).

**Нативний `window.confirm()` не використовується.** Він не стилізується, не темизується,
не локалізується і виглядає як системна помилка, а не як частина продукту.

**Reference.** `confirmDiscard()` — канонічний діалог «Discard unsaved changes?»
(`[Keep editing, Discard changes (destructive)]`), реалізовано 12.08.2026.
Для видалення з impact preview — `credDelete` → `credConfirmDelete`.

**Examples.**
- ✅ `checkDelete`, `policyDelete`, `policyEditDelete`, `cmConfirmRemove`.
- ✅ Миттєво й правильно: `ssRemoveFolder`, `pdRemoveTag`, `peRemoveTag`, `ecRemoveValueCheck`, `ciRemove`.
- ✅ **Виправлено 12.08.2026.** `confirmDirty` викликав нативний `window.confirm` — єдиний
  браузерний діалог у продукті з повністю кастомною модальною системою. У кодовій базі не
  лишилось жодного `window.confirm`.
- ✅ **Виправлено 13.08.2026.** `deleteSavedView` — persisted-сутність зникала миттєво.

**Exceptions.** Дія з доступним undo (§14.1) може обійтися без модалки — undo замінює
підтвердження. Одне з двох, не обидва.

# 7. Statuses

## 7.1 Носій статусу

**Rule.** Статус несе **один** компонент — канонічний бадж `.bdg` (Design System §12). Ручних
пігулок не існує.

**Правило рядка:** у рядку рівно **один** обʼєкт із формою. Значення (`Enabled` › `Disabled`)
ніколи не отримує рамку чи фон — інакше ієрархія «дані vs метадані» руйнується, а колір
кодується двічі. Значення = `.bdg--quiet`; пігулка лишається за статусом.

**Reference.** `.bdg` — одна геометрія · 6 кольорів · 3 варіанти (Figma `2988:70572`).

**Examples.**
- ✅ 13.08.2026 десять незалежних badge/pill-родин зведено до одного компонента через селектори,
  без правок розмітки й JS.
- ✅ Severity: critical → Red · high + medium → Orange · low → Blue · pass → Green.

**Exceptions.** Detected Drift — свідомий виняток: статус узгодження (Unreconciled / Flagged /
Reconciled) є **заповненою пігулкою**, бо він визначає наступну дію; тип зміни (Added / Modified /
Removed) — тихий кольоровий маркер без заливки.

## 7.2 Словник статусів інтеграції

**Rule.** Життєвий цикл інтеграції описується закритим набором:
**Available → Connect → Connected → Attention → Error → Disabled**. Інших слів не вводити.

Статуси **capability** — окремий закритий набір: **Enabled / Disabled / Issue**. Два набори
не змішуються.

**Reference.** Мапа `INTG_STATUS`.

**Examples.** ✅ `notset` → «Available» (узгоджено із заголовком секції «Available integrations»
і кнопкою `Connect`); ✅ `attention` → «Attention» (був помилково «Connected» на amber-баджі).

**Exceptions.** Немає.

## 7.3 Severity як контрол

**Rule.** Дропдаун вибору severity використовує **нейтральне** оформлення контролу + маленьку
**кольорову крапку** біля завжди присутнього текстового лейбла. Заливати все поле кольором
severity заборонено.

Колір живе тільки на крапці: critical `#FB3C44` / high `#F97316` / medium `#F59E0B` / low `#3B82F6`
— однаково в обох темах.

**Reference.** `.pe-sev-btn` + `.pe-sev-dot`, попап `#pe-sev-pick`.

**Examples.** ✅ 9 екземплярів у policy-create step 2 і policy-edit.

**Exceptions.** Немає. Той самий принцип діє для будь-яких state-боксів (current ↔ expected,
before ↔ after): нейтральна поверхня + кольорова крапка, ніколи суцільна червона/зелена заливка.

# 8. Errors

## 8.1 Носій за масштабом

**Rule.** Помилка завжди має **червону** семантику і завжди дає **шлях відновлення**.
Носій обирається за масштабом:

| Масштаб | Носій |
|---|---|
| Поле форми | inline під полем (§13) |
| Дія на екрані | toast варіанта `error` (§14.1) |
| Крок флоу не вдався | inline-блок у місці кроку + кнопка retry |
| Сторінка / дані недоступні | повноекранний error screen із поясненням і дією |

Текст називає **причину** і **наступну дію**. «Something went wrong» без дії — не помилка,
а тупик.

**Reference.** Connect-test в agentless-онбордингу — фейл показує причину й дозволяє виправити
ввід та перетестувати **не виходячи з кроку** (той самий патерн, що CN-03).

**Examples.**
- ✅ AWS Stage 1: account ID можна виправити й перетестувати всередині Stage 1.
- ✅ **Виправлено 12–13.08.2026.** Пʼять помилок валідації показувались у **зеленому** success-toast
  із галочкою — помилка виглядала як підтвердження успіху. Найгрубіше порушення семантики кольору
  в продукті. Переведено на `error`, потім на inline-шасі (§13).

**Exceptions.** Немає. Помилка, показана не червоним, — дефект.

## 8.2 Error screen

**Rule.** Повноекранна помилка: ghost-red коло `rgba(251,60,68,0.08)` + SVG **circle-info**
`stroke #FB3C44`; рядок-підсумок `N errors found`; кнопка повтору **«Try again →»**.

**Reference.** J3 connect-failed.

**Exceptions.** Немає.

## 8.3 Retry

**Rule.** Повтор відбувається **у тому ж місці**, де сталась помилка. Відкидати користувача на
початок флоу заборонено — це втрата вже введених даних.

**Reference.** Connect-test: `Try again` перезапускає тест, лишаючись на кроці.

**Exceptions.** Помилка, що робить весь контекст недійсним (сесія протухла), може вимагати
повернення на початок — але тоді про це сказано явно.

## 8.4 Warning

**Rule.** Warning — стан, що **не блокує**, але змінює рішення: «дія спрацює, але наслідок може
бути не той, якого ти очікуєш». Показується **до** дії, а не після.

Розрізнення: **error** = не вийшло · **warning** = вийде, але зважай · **info** = просто контекст.
Якщо повідомлення не змінює поведінку користувача — це не warning, а шум.

**Reference.** Impact preview у `credDelete` — перед видаленням показує, **скільки нод залежать**
від цього credential.

**Examples.** ✅ `credDelete` — еталон «destructive with impact preview».

**Exceptions.** Warning не використовується для успішного результату із застереженням
(«Imported 8 of 10») — це `info` із деталізацією.

# 9. Empty States

## 9.1 Канонічний порожній стан

**Rule.** Порожній список ніколи не буває просто порожнім. Канонічний блок: **icon-circle 44×44**
+ заголовок **14px / 600** + підпис **12px** + дія. Типів порожнечі рівно два:

| Тип | Причина | Дія |
|---|---|---|
| **no-match** | фільтр або пошук нічого не знайшов | reset-посилання «Clear filters» |
| **true-empty** | сутностей не існує взагалі | filled `btn-primary` CTA, що створює першу |

Плаский центрований рядок тексту без іконки, заголовка й дії — **не** empty state.

**Носій — клас, не inline:**

```html
<div class="es">                       <!-- .es.es-sm — компактний варіант у панелі/картці -->
  <div class="es-ico"><svg …></svg></div>
  <div class="es-title">…</div>
  <div class="es-sub">…</div>
  <div class="es-act"><button …></button></div>
</div>
```

Клас `.es` тримає всі канонічні значення, тому новий стан не потребує **жодного** нового CSS.
Ставити `font-size` / `color` інлайн поверх `.es-*` заборонено.

**Reference.** `.es`. Робочі зразки: `nd-attrs-empty` (no-match + `Reset filters`),
`cmd-nodes-empty` (true-empty + `Assign nodes`), порожній `intg-list` (true-empty + `Add integration`).

**Examples.**
- ✅ Credentials, Nodes, Scan Schedules, CM Groups — приведені до канону 07.08.2026.
- ✅ Сім text-only станів переведено на `.es` 13.08.2026; `report-empty` знято з 16px/700 на 14/600.
- ✅ no-match отримав робочий reset: `ndResetAttrFilters()` чистить і пошук, і статус-фільтр.
  **Reset без обробника — не reset.**

**Exceptions.** Порожня комірка всередині заповненого рядка («—» у колонці) не є empty state.
Порожній стан у dropdown або поповері обмежується одним рядком тексту: icon-circle 44×44
в контейнері 240px непропорційний. Чинний виняток — `recon-node-empty`.

# 10. Terminology

## 10.1 Назва кроку = заголовок сторінки

**Rule.** Крок у stepper і заголовок сторінки, на яку він веде, називаються **дослівно однаково**.
Розбіжність робить індикатор недостовірним: користувач читає одну назву в навігації і іншу
в контенті.

**Reference.** AWS-інтеграція GWB-6638 — **Connect AWS · Node Discovery · Node Inventory** (CN-08).

**Examples.**
- ❌ `#j3-step-nav` показує вайрфреймові `Connect AWS · Sync Nodes · Run Scan · Results`, тоді як
  сторінки називаються **Node Discovery** і **Node Inventory**.

**Exceptions.** Скорочення в stepper допустиме, якщо повна назва не вміщується — але лише
усіканням зі збереженням початку («Node Discovery» → «Discovery»), не синонімом.

## 10.2 Exit vs Skip

**Rule.** Це дві різні дії, і вони не називаються одним словом.

| Дія | Лейбл | Результат |
|---|---|---|
| Вийти з флоу | **Exit** | флоу покинуто, повернення на попередній екран |
| Пропустити необовʼязковий крок | **Skip** | флоу триває, крок лишається незаповненим |

Одне формулювання на кожну дію в межах усього продукту.

**Reference.** `Exit` у stepper-хедері онбордингу.

**Examples.**
- ❌ Було пʼять формулювань. ⚠️ Перевірка показала, що це **три різні речі**, а не одна дія
  з пʼятьма лейблами: справжній вихід із флоу (→ `Exit`), справжній Skip (не чіпати) і два
  сегменти `.toggle-group`, яким потрібна **назва опції**, а не дієслово дії.
  При правці термінології звірятися з цим поділом.

**Exceptions.** Немає.

## 10.3 Граматика повідомлень

**Rule.** Повідомлення про результат: `<Сутність> <дієслово в past tense>`.
Без «successfully», без крапки в кінці, без гліфів у тексті.

**Reference.** «Credential updated».

**Examples.** ✅ «Assignment saved», «Draft saved». ❌ «Policy saved successfully»,
«Mapping activated successfully».

**Exceptions.** Повідомлення з числами конкретизує обсяг: «8 nodes imported» — коректно.

## 10.4 Літеральне значення — не бадж

**Rule.** Значення, яке користувач **вводить або звіряє** (`node_group`, `CI0043221`, назва
колонки CSV), — це `.code-tag`, а не бадж. DM Mono 11px, **регістр збережено**.

Канон баджів тут не застосовується свідомо: 9px UPPERCASE перетворив би `node_group` на
`NODE_GROUP`, а регістр значущий.

**Reference.** `.code-tag` (Design System §13.1).

**Exceptions.** Моно-текст усередині **комірки таблиці** лишається простим текстом — колонка
вже є контейнером.

# 11. Progress Feedback

> Розділ навмисно відокремлений від §12 Loading. Раніше обидва були одним правилом, і це
> призводило до того, що довга операція показувала спінер, придатний для 300 мс очікування.

## 11.1 Довга операція

**Rule.** Операція, ініційована користувачем і триваліша за ~2 с, показує **що саме зараз
відбувається**, а не факт очікування. Прогрес описується конкретно («Scanning us-east-1…»),
не абстрактно («Loading…»).

Операція, що може тривати понад ~10 с, додатково дає **вихід без скасування** — «Continue in
Background» — і явно каже, **де зʼявиться результат**, коли буде готовий.

**Reference.** **Node Discovery** у GWB-6638 (CN-10) — спінер + рядок поточного статусу +
«Continue in Background» + фраза про те, що знайдене зʼявиться під **Detected Nodes**.
Еталон для всіх довгих операцій.

**Examples.**
- ✅ `j3-syncing`, `cmdb-importing`, connect-test — покроковий чекліст із поточним станом.
- ❌ Операції, що показують лише спінер, не кажучи, чого чекати.

**Exceptions.** Фонові автооновлення (sync, polling) не блокують екран і прогресу не показують —
позначаються лише часом останньої синхронізації.

## 11.2 Багатоетапна операція

**Rule.** Операція з відомими етапами показує **чекліст етапів**, а не один індикатор:
пройдені — з галочкою, поточний — активний, майбутні — тихі. Користувач бачить, скільки лишилось.

**Reference.** Connect-test в agentless-онбордингу.

**Exceptions.** Операція, кількість етапів якої невідома наперед, показує лише поточний етап
без загальної кількості.

# 12. Loading

## 12.1 Поріг індикатора

**Rule.** Очікування коротше за ~400 мс індикатора **не отримує** — миготіння спінера гірше за
його відсутність. Від ~400 мс до ~2 с — індикатор активності. Понад ~2 с — це вже §11.

**Exceptions.** Немає.

## 12.2 Місце індикатора

**Rule.** Індикатор зʼявляється **в межах області, яка оновлюється**, а не поверх усього екрана.
Завантаження таблиці не блокує сайдбар і тулбар.

Кнопка, що запустила операцію, переходить у стан `loading` і стає недоступною — це запобігає
подвійному сабміту й показує звʼязок «я натиснув це — чекаю на це».

**Reference.** Стан `loading` канонічних кнопок (Design System §6.5).

**Examples.**
- ⚠️ Типи `Third` і `Back` у канонічному наборі **не мають** стану `loading` — дефект макета,
  винесений дизайнеру (§16).

**Exceptions.** Первинне завантаження екрана може блокувати всю область контенту, бо часткового
контенту ще не існує.

# 13. Validation

## 13.1 Місце помилки

**Rule.** Помилка валідації показується **біля поля, яке її спричинило**, а не глобально.
Два шасі — за типом контейнера:

- **Full-page форма:** кнопка submit **disabled**, поки форма невалідна, + текстовий hint, чого
  бракує. Користувач не має натискати, щоб дізнатися про помилку.
- **Модалка:** submit активний; при натисканні невалідні поля отримують червону рамку `#FB3C44`
  + фокус на першому невалідному, і рамка **автоматично знімається** при першому вводі в це поле.

Валідаційна помилка **ніколи не показується як toast**: toast не вказує на поле й зникає раніше,
ніж користувач встигне його виправити.

**Носій — хелпер, не копіпаст:**

| Функція | Призначення |
|---|---|
| `vRequire(ids)` | Модалка. Рамка на порожні поля, фокус на перше, auto-clear при вводі. Повертає `true`, якщо є порожні |
| `vFormError(host, msg)` | Помилка рівня форми: inline-блок `.v-form-err` угорі `host`. `msg = null` знімає. Знімається сам при першому `input`/`change` |
| `vMarkField(el)` | Позначити одне поле за нестандартної умови |

`gmGoStep` очищає `.v-form-err` при зміні кроку — помилка одного кроку не переїжджає на наступний.
Full-page шасі має класи-носії `.v-submit:disabled` і `.v-req-hint`.

**Reference.** Full-page — `alValidate`, `ssValidate`. Модалка — `vRequire` в `icxNext`.

**Examples.**
- ✅ **Закрито 13.08.2026.** Пʼять валідацій, що показувались у зеленому success-toast, переведені
  на inline-шасі — по одному шасі на форму. У продукті не лишилось жодної валідації через `showToast`.

**Exceptions.** Помилка, що стосується форми в цілому, а не конкретного поля («Connection test
failed», «Select a provider»), показується блоком `.v-form-err` угорі форми — але теж не toast.

## 13.2 Момент валідації

**Rule.** Валідація не спрацьовує, поки користувач ще друкує. Перевірка — на `blur` або на submit;
зняття помилки — на першому вводі. Показувати червону рамку на другому символі email заборонено.

**Exceptions.** Перевірки доступності в реальному часі (унікальність імені) показують результат
під полем як інформаційний, не як помилку, поки поле не покинуто.

# 14. Action Results

## 14.1 Toast

**Rule.** Результат дії, що не змінює екран, повідомляється **одним toast-компонентом** із
варіантами `success · error · warning · info`. Колір та іконка — властивість **варіанта**,
не тексту повідомлення.

- Один компонент на весь застосунок. Двох паралельних систем не існує.
- Гліфи `★ ✓ ⚠` не пишуться всередині рядка повідомлення.
- Toast повідомляє про **результат**, а не про **процес** (§11) і не про **валідацію** (§13).
- Дія, наслідок якої видно на екрані (рядок зник, бейдж змінився), toast не потребує.

**Reference.** `showToast(message, variant)` — реалізовано 12.08.2026. Варіант керує фоном
(`#success-toast[data-variant]`), іконкою (`_TOAST_ICON`) і тривалістю (`_TOAST_MS`:
success / info 2800 мс, warning / error 3800 мс — помилка має жити довше, бо на неї треба
відреагувати).

Фон задається **CSS-правилом за `[data-variant]`**, не inline: інакше `_syncInlineTheme` мутує
його й ламає колір. Фон однаковий у light і dark — toast є суцільною темною поверхнею.

**Examples.**
- ✅ Одна система: `scToast` — тонкий аліас на `showToast(msg, 'info')`; окремий одноразовий div
  з hardcoded фоном видалено. Захисні розгалуження `typeof scToast === 'function' ? … : …`
  знешкоджені.
- ✅ Гліфи винесено з тексту у варіант: `'★ Baseline set to …'` → `showToast('Baseline set to …', 'success')`.
- ✅ Зворотна сумісність: `showToast(msg)` без варіанта = `success`, тому ~25 наявних викликів
  не змінювались.

**Exceptions.** Незворотна дія над persisted-сутністю може показати toast із **undo** — тоді
тривалість збільшується. Це єдиний випадок, коли toast несе дію.

## 14.2 Тиша як варіант

**Rule.** Успіх підтверджується **найтихішим достатнім способом**. Ієрархія згори вниз:

1. Зміна на екрані сама по собі (рядок додався, статус змінився) — нічого більше не потрібно.
2. Toast варіанта `success` — якщо результат не видно.
3. Success-екран — **лише** для завершення багатокрокового флоу, з чіткою наступною дією.

**Exceptions.** Незворотні або дорогі операції (видалення інтеграції, імпорт сотень нод) можуть
отримати success-екран навіть поза багатокроковим флоу: користувачеві потрібне однозначне
підтвердження, що операція завершилась.

## 14.3 Success screen

**Rule.** Канонічний екран успіху: коло **56×56**, ghost-green фон `rgba(37,167,96,0.1)`,
24–28px SVG-галочка `stroke #25A760`; заголовок 20px/800 **без знаку оклику** («Policy created»,
не «Policy created!»); підзаголовок 12–14px; опційна міні-статистика; CTA — filled `btn-primary`.

**Reference.** CMDB complete · Policy Create · «Connection Manager active».

**Exceptions.** Немає.
